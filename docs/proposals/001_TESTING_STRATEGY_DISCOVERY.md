## 0. 摘要与建议

**Veripaka 的核心问题不只是“怎样复用一个测试”，而是“Agent 怎样判断一个真实对象应该如何被检验，并探索出有检出力的方法”。**

用户已明确的重心：

- “如何探索真实、高能动性的 test recipe”在前；evidence-verification 是必要支撑，不是主要卖点。
- 能动性还包括更 meta 的判断：对象的基础属性影响测试方式，例如网页的模态会影响 DOM、实际渲染图像等观察方式的选择。

本提案建议：

1. 将“搜索面”理解为**测试决策的问题空间**，而不是首先实现一个新的搜索引擎。
2. 优先积累带条件、理由和反例的测试策略知识；具体表示先用少量可读文本，不新增一套与 Recipe 并行的机器对象。
3. 在 S2 的真实路径中检查 Agent 是否能自主选择观察层、干预与判据；不要用“接通一个视觉工具”代替方法探索能力的验证。
4. 用小规模对照与迁移任务检验这些建议；没有价值时缩减或放弃新表示，不以文档数量证明产品进展。

**本轮不建议建设：**通用对象本体、七轴必填 schema、独立 best-practice registry、向量库、自动模型调度或通用测试规划引擎。

依据包括本轮用户澄清、[原始 brief](../Draft.txt)、[介绍草稿](../intro_draft.txt) 和当前设计/验收。下文例子是设计推演，未在本轮运行跨领域实验或核验外部工具；不能作为广域有效性的证据。

## 1. 自我反思：上一轮归纳哪里仍有问题

| 上一轮的有用启发 | 仍可能走偏的地方 | 本提案的修正 |
|---|---|---|
| 对象属性影响测试方式 | 把“frontend → 图像”“异步 → 等待”做成一一映射 | 选择取决于对象、待证主张、环境与可用控制手段之间的关系 |
| 模态、时间、可观察性等可启发检索 | 七个维度混合了对象属性、任务要求和执行条件，既不正交也不完备 | 将其当作按需使用的问题提示，不作为所有任务的必填标签 |
| 跨领域的策略可能复用 | 多举几个例子并不证明抽象真的能迁移，统一术语也可能抹掉关键条件 | 既测适用迁移，也测不适用的近似情形；保留具体领域知识 |
| Agent 应主动探索 | 容易把更多工具调用、更多故障注入当成更高能动性 | 能动性也包括直接复用足够好的方法、选择便宜的观察，以及及时停止 |
| 探针可用于区分解释 | 不一定存在足够的可观察性或控制能力；干预也可能改变对象而引入混淆 | 先检查实验是否有区分力及其干扰，不可判定时报告局限，而非无限试探 |
| 用假说与反例描述测试 | 可能把所有测试缩成两个预先已知的解释，遗漏开放式探索、规范符合性与体验判断 | 允许先认识行为、形成问题，再选择判据或实验；不能强迫每次观察都预设一个已知 bug |
| 保存“条件 → 策略”知识 | 可能又造出一个厚重格式层，重演把结构当产品价值的错误 | 文本先行；仅在真实消费暴露需要时提升为稳定字段 |
| 检出代表性故障可校准方法 | 有针对性的一个 mutation 很容易成为作者与测试共同过拟合的样本 | 加入未告知作者的故障/正常变体和不适用对象，不据单例声称普遍可靠 |
| 核验真实执行能避免空话 | 真实执行一个无关测试仍可能回答错问题 | 分开判断目标相关性、方法区分力、执行有效性；三者不能互相代替 |

我此前还把介绍写成了“用户已经设计好测试，Veripaka 负责保存与重跑”。这把最需要产品帮助的工作留给了用户。后来改成“探索方法”，仍可能默认对象和可观察性已经清楚。本轮要补上的正是**对测试问题本身进行建模、求证和修正**的能力。

反过来，也不能因为强调方法探索就否定 S1：它证明了有限范围的执行与冷复用基础。其结论保持不变，但不再被解释为核心方法探索能力已经成立。

## 2. 能动性：选择并修正测试问题的表示

一个测试决策至少受到三类因素共同约束：

- **对象与环境：**表现形式、状态归属、生命周期、部署/消费边界、依赖、随机性等。
- **待证主张：**用户到底要求什么，正确性依据来自哪里，哪些风险只是新发现而未获确认的范围。
- **可用手段：**能观察什么、控制什么、如何恢复，有什么工具、权限、成本与时间限制。

这些不是应填满的表格。每次只追问会改变当前测试选择的未知；已知且充分时直接应用现有方法。

### 2.1 网页例子的关键修正

同一网页同时具有像素呈现、结构语义、输入行为和业务状态。DOM 与图像不是两套互斥的“前端测试模式”：

- 判断文字是否被遮挡、阴影是否异常，需要覆盖真实呈现；只检查 DOM 节点存在不够。
- 判断控件的语义角色或可访问名称，结构化树通常更直接；截图不充分。
- 判断按钮是否真的触发保存，需要输入及后续状态观察；视觉正确不等于行为正确。

所以选择逻辑不是“识别项目类型 → 选工具”，而是：**这一主张依赖哪些信息？当前表示丢掉了什么？需要怎样补充或转换观察？**

“真实”也不等于所有测试必须端到端、必须生产环境或禁止 mock。测试边界应与主张相称；较小的真实函数测试可能已足够，mock 的局部结论不能冒充它替代掉的系统行为。

### 2.2 能动性不要求总是生成新方法

合理动作可能是：复用已有 Recipe、缩小探针、增加一个观察点、选择独立读取者、调整采样、查询规范、提出必要澄清，或明确当前不可判定。

并非每项测试都从两个已知假说起步。开放式巡视、行为/状态地图、基于适用规范的检查，以及体验问题的发现也有价值；此时先获得有范围的观察、形成值得追问的问题，不强造精确 expected 或已知故障。后续再将可验证的部分收敛为检查。

不知道预期行为时不能从现有实现反推“它这样做就是正确”。需要区分需求、适用标准、实现事实与待确认假设；合理澄清不是产品失败，所有问题都退回用户也不是能动性。

## 3. 搜索什么：条件化的测试决策知识

这里的 best-practice 不宜意味着“普遍最优做法”。更准确的是：**在一定条件下，值得尝试且可被检验的测试策略。**

保留上一轮的模态、状态/时间、可观察性、可控制性、判据、变异/尺度、风险/边界等提示，但将它们用于发现决策缺口，而非完成分类任务。

### 3.1 可迁移的是关系，不只是术语

| 决策缺口 | 候选策略 | 必须保留的条件/反例 |
|---|---|---|
| 节点存在，但是否实际可见未知 | 获取真实呈现，检查相关区域与上下文 | 语义主张可能优先查结构；图像存在也不等于已检验内容 |
| 读写可能共享短寿命状态 | 引入独立读取者，或越过相关生命周期边界 | 新进程仍可能共享下层缓存；仅承诺会话内状态时不应擅自要求服务端持久化 |
| 结论依赖事件顺序或最终收敛 | 观察历史，控制有意义的延迟/重复/乱序，按约定等待条件 | 先查明一致性承诺；固定 sleep 不等于时序判据，立即一致性也不能被降成最终一致 |
| 没有便宜的逐例标准答案 | 找锚点样例、独立参考或有领域依据的变形关系 | 不变量可能被恒定/空输出满足；独立实现也可能共享错误假设 |
| 输出有随机性或性能分布 | 区分单次性质与统计主张，设计样本、分层和测量条件 | 固定 seed 有利于复现但不能单独证明一般可靠性；均值可能遮蔽子群或尾部问题 |
| 测试动作有不可逆副作用 | 建立隔离与恢复路径，再按需注入失败 | dry-run 不能替代真实执行；某些副作用无法在预算和权限内安全测试 |
| 源码可运行，但交付对象未被检查 | 在实际产物及独立消费环境验证入口 | 不必每个局部算法测试都重新打包；共享全局依赖可能污染消费者环境 |
| 相同行为依赖不同主体关系 | 改变主体/资源归属，检查允许与拒绝路径 | 管理员成功不是权限边界证明；前端隐藏控件不是服务端拒绝 |

这些是搜索种子，不是覆盖所有领域的默认套件。工具名应留在实现/绑定阶段；只有真实能力或限制会影响选择时，才成为检索条件。

### 3.2 建议的一种轻量知识写法

先用自然语言表达以下内容，不规定新 schema：

> **何时考虑：**什么未知或假通过风险触发这条策略？  
> **要回答什么：**当前问题或需要区分的可能性是什么？若尚不清楚，先观察哪些行为以形成问题？  
> **怎么做：**建议的观察/干预，以及不同结果意味着什么。  
> **为什么有用：**区分力从何而来，有哪些前提？  
> **何时不用：**反例、副作用、停止条件或更便宜的充分方法。  
> **依据与经历：**规范/资料来源、项目案例、失败经验与未知；资料中的建议不冒充本项目实测。

例如“独立读取”策略的价值不在于写下“重启进程”，而在于保存：当前观测可能只来自写入者自己的状态；引入真正独立的读取者能排除哪种解释；为什么换一个客户端可能仍然不够。

领域名和关键词仍有用。所谓 meta 层不意味着抛弃数据库语义、浏览器行为或数值分析等具体知识，靠抽象推理包办测试。

## 4. 搜索与探索怎样配合

建议的交互循环如下，允许跳过不必要的环节，也允许回到前面：

```text
目标与初始观察
  → 找出影响决策的未知 / 假通过风险
  → 复用现有方法，或检索条件化策略与领域依据
  → 核对本项目的适用前提、能力与权限
  → 选择一个能改变判断的观察或干预
  → 根据实际结果修正对象认识或下一步策略
  → 已有足够方法时收敛、校准并保存；否则保留未知或停止
```

### 4.1 至少区分三种“找”

1. **找项目里已存在的 Recipe。** 可能已经足够，不应每次重新研究。
2. **找如何设计/调整方法的知识。** 例如“共享缓存导致观测不独立”而不是仅搜“settings test”。
3. **查明当前对象和工具事实。** 实际入口、状态归属、可用采集能力、版本限制等，不能由通用策略文本代替。

外部资料查询是第二类的一种可选来源，不要求所有项目联网，也不默认每个任务都进行开放式网络搜索。引用外部建议时要核查来源与适用版本；不能从命中的文档自动获得执行授权。

S1 的 `find` 目前只是本地 Recipe 元数据/正文检索。自然语言的元层查询**不是**现有 CLI 已具备的能力。初期可由 Skill 帮助形成查询、读取少量参考并驱动宿主已有工具；不要先把“搜索面”翻译成服务、索引和新命令。

### 4.2 记录决定，不要求冗长推理仪式

一个有用的短记录可以是：

> 当前 GET 可能命中同进程缓存，不能据此判断持久化。拟用同一数据目录启动独立读取进程；若仍共享缓存则需换观察边界。当前任务未要求跨设备同步，不扩大主张。

记录外显的关键决定、所依据的观察和未决条件即可，不要求完整思维链或每个工具调用都填写一份表。也不虚构信息增益分数：目前只需说明一个探针的不同结果是否会改变下一步选择。

### 4.3 探索不等于事后改变正确答案

可以调整探针、补充观测、修正对象认识和提出新的方法草稿。不能在看到失败后原地降低 expected、删除 required 或缩小承诺来制造 pass。

方法选择可在准备阶段发生；调查中可以在既定范围内调整探针；verification 内只能选择计划允许的输入或分支，变更判断标准则另建计划。不要求把这一循环全部塞进一个不断变动的 verification run。

方法准备和调查可以产生新假设；稳定的 verification 仍需按冻结计划判定。S1 的 `apply` 不因此变成自动探索入口，手工/宿主探索材料也不会因此升级为 S1 的受管可执行证据。尚不支持的来源、mode 和 kind 仍按现行边界处理。

## 5. 对 Veripaka 的具体启发

### 5.1 区分内容职责，不急着增加机器对象

| 内容 | 主要职责 | 初期可以怎样承载 |
|---|---|---|
| 策略性知识 | 帮助选择观察、干预和判据，说明何时不用 | 现有 Skill 的少量参考正文，或 Recipe 的 references；仅为候选落点 |
| 项目 Recipe | 将策略落到具体对象、主张、步骤/分支和限制 | 继续使用 RECIPE.md，不另造通用 workflow DSL |
| 本次探索记录 | 保存发现了什么、为什么切换策略、还缺什么 | 简短会话/调查记录；是否形成独立文件由实际复用需求决定 |
| 冻结 Plan / evidence | 为一次判断提供明确范围与实际材料 | 保留已有职责，不把方法选择质量交给摘要或 schema 保证 |

这四类是内容用途，不是四套必须新建的库、版本系统或 CRUD。若一段通用正文已经能帮助 Agent 做对选择，就没有必要先拆成可编程的策略卡片。

### 5.2 Agent 应有多种合法出口

- 已有方法相关且充分：直接应用。
- 已找到策略，但项目条件不匹配：调整绑定/探针，建立新方法候选。
- 观察改变了对对象的认识：说明变化并切换策略，不照抄模板。
- 缺判据、权限或安全恢复条件：提出有针对性的澄清/前提，或保留不可判定。
- 探索没有产生可复用知识：只记录本次结果，不强制产出 Recipe 凑数量。

“每次都生成一条新 Recipe”与“每次都通过”一样，不应成为产品优化目标。

### 5.3 现行设计如何受影响（待接受后合并）

| 文件/章节 | 建议改动 | 不改动什么 |
|---|---|---|
| 组合设计 §1 | 把对象认识、方法发现与校准显式放在复用之前；允许充分方法的快速路径 | 不接管整个开发循环，不预设广域自主能力已成立 |
| 组合设计 §4 | 补充策略的适用条件、可调整部分、探索与判据的边界 | 不立即扩展 Recipe schema，不改 apply 的无执行职责 |
| 组合设计 §9 | 区分 Recipe 查找、策略知识查找与对象/工具事实查明 | 不直接承诺语义检索、通用索引或新工具适配 |
| 阶段 S2 | 在 S2-1 的真实视觉/guided 任务中检验方法选择，而不只给定方法让 Agent 执行 | 保留调查、对象身份、参考生命周期的既有边界；不追加一整套 M0 |
| 阶段 S3 / S4 | 用方法迁移与对照验证知识是否真的降低重复设计劳动 | 不用这次小样本替代正式收益评估，不预设 CLI 有净贡献 |

当前阶段文件中“已收敛、不再 brainstorm”的措辞记录的是前一次实施收敛，不禁止用户现在要求的新提案。这里讨论的是核心产品重心的校准，不是恢复已封存的几套架构。**本文件本身不修改 S2 的现行范围或 S1 的历史结果。**

## 6. 怎样检验：是否真的改变了测试决策

### 6.1 最小试验建议

在 S2 的一个真实视觉/guided 主任务中使用候选策略正文，并用少量非视觉/近似反例作迁移 pilot。不要先覆盖前述所有领域；也不要让策略知识格式的完善成为接通真实路径的前置阶段。

样例池可包含以下三个对比，实际挑选要由可用对象和工具决定：

| 对比 | 希望观察到的能力 | 不能提供给 Agent 的捷径 |
|---|---|---|
| 同一网页：视觉遮挡 vs 语义角色问题 | 对不同主张选择不同观察层；必要时组合而非偏爱单一模态 | 不预先告诉它必须截图或必须查 DOM，不提供现成目标 Recipe |
| 相近状态接口：承诺跨重启持久化 vs 仅会话内状态 | 识别生命周期和承诺差异，避免把“重启测试”当万能法则 | 不把异常情形或预期测试步骤直接写进任务提示 |
| 独立消费环境 vs 作者环境 | 发现被全局依赖/替代入口掩盖的问题，或判断何时无需切换环境 | 不预先指明缺失文件、错误配置或隐藏故障位置 |

Agent 可以看到合理的用户需求、项目资料和真实对象；“不给捷径”不等于故意隐藏必要需求。缺必要需求时，应把适当澄清作为可接受行为。

### 6.2 对照与判定

- 固定模型、工具权限、任务、执行预算和执行/证据基础，比较通用自测指导与“同样指导 + 候选策略正文”。双方获得相同的目标事实与工具资料；策略组不能额外得到故障位置，文本和实际运行开销分别记录。这只试探策略内容的增量，不用于宣称 CLI 贡献；现行 S4 的文档/CLI 分离问题仍保留。
- 不先提供为该任务写好的完整 Recipe，否则测到的主要是查找与遵循，而不是方法形成。
- 对照使用隔离副本和独立新会话，平衡顺序，保留失败、超时和缺前提样本；运行遵守项目 README 的模型与会话约束。
- 出题/故障构造与方法生成分离。除校准样例外，准备未告知方法作者的正常/故障变体及不适用近邻；不得让隐藏答案进入提示或策略文档。
- 事先确定哪些行为/结论构成有效回答，允许多种合理策略，不按是否采用某个工具名或是否复述策略文档评分。
- 由独立行为检查、可复核的对象事实或盲审判断结果，不用 Agent 自评或措辞流畅度当真值。

应观察：目标相关性、真实区分力、错误拒绝正常对象的情况、对反证的调整、恰当停止、冷会话迁移，以及人工补充/复核劳动。工具次数与耗时只作成本和过程数据，不作为能动性分数；无法计量的成本标 unknown。

每个“用了策略且成功”的样例都要追问：**它是否真的换了一个更合适的观察/实验，还是原本就会做对，只是多写了一段解释？**

### 6.3 什么结果会否定或缩减本提案

- 分类和记录开销增加，但实际测试选择没有改善：删减提示/表示，不继续加字段。
- 策略只在训练样例有效，换对象或条件就误用：收窄适用域，保留领域方法，不宣传通用层。
- 普通模型加现有项目文档已足够：承认新增正文的净贡献不足，不靠更多 token 强行制造优势。
- Agent 只会泛泛提出建议，仍需用户设计所有可执行步骤：核心方法探索能力尚未交付。
- 正确结果主要来自预埋好的完整 Recipe：将结论归为复用能力，不归为方法发现。
- 工具或前提不具备，无法检验策略：先记录 blocker，不能据此证明策略有效或无效。

pilot 用于取舍，不直接给出一般成功率或收益承诺。是否扩大试验由观察到的问题和最低有用改善要求决定，不预设“新知识层一定值得建”。

## 7. 待决策项与文档去向

用户已明确的产品重心不是本提案等待重新批准的事项；待讨论的是实现与验证路径：

1. 是否采用“条件化策略正文 + 实际任务”的最小起步，而不先建设独立知识对象？
2. 如何把方法选择要求融入现有 S2-1，而不将其变成仅执行已给定视觉步骤的演示？
3. 第一对迁移/不适用样例选什么，谁持有独立预期与隐藏变体？
4. 观察到什么内容重复和消费需求后，才值得增加稳定元数据或检索实现？

建议先接受最小起步与评价方向，在真实任务里迭代；具体 schema、命令、数据落点和广域覆盖保持未定。接受的内容应分别合并到组合设计和阶段文件，P001 只保留取舍依据，不成长为第二份权威设计。
