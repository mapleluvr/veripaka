一、两份已经一致的部分，不必继续争论

以下不是两种不同路线，而是已经形成共同结论：

- 产品是方法库＋有界应用＋证据反馈，不是全自动开发平台。
- Recipe 不等于脚本、用例或一次运行。
- 方法、项目绑定、Profile、Plan、Run 的语义要分开，但不必各建一个子系统。
- 使用 Markdown 正文加结构化元数据，保留方法解释。
- 真实测试继续留在原框架中，不迁移到 Veripaka 重写。
- 不能把 exit 0、截图存在、调用完成当作业务通过。
- 方法升级不能静默改变项目判据。
- pi 消费路径、搜索和冷上下文复用应早于复杂 delta、全局库、并发和 dashboard。
- 便宜模型能否因此更经济，需要实验。

因此，现在的主要工作不是继续 brainstorm 定位，而是把少数关键契约收敛到可实现程度。

三、这份真正比上一份更好的地方

1. 它把“不要假通过”推进到了具体接纳规则

上一份主要规定：

▎ 记录来源、目标身份和证据，不得把缺失算通过。

这份进一步回答：

- 谁能把材料标为 command-captured？
- invocation 是否真的属于这个 run？
- 捕获的进程结果如何映射到冻结的 check？
- 外部提交 JSON 是否能直接升级为执行证据？

见 docs/veripaka-target-shape.md:443。

这是实质进步。否则实现很容易变成：

Agent 写一份 results.json
→ schema 合法
→ CLI finalize
→ “程序计算出的通过”

看似把判断交给程序，实际上只是让程序给模型自述盖章。

这份明确阻断了这条路径，上一份在这里不够具体。

2. 它区分“观察了某个服务”与“验证了当前代码”

见 docs/veripaka-target-shape.md:472。

上一份知道 Git HEAD 不够，但仍停留在记录身份和检查漂移。

这份直接规定：

- 声称验证 checkout/build/deployment，必须建立对应身份。
- 身份不明时，最多在预先声明的 endpoint-observation 范围报告观察结果。
- 不能把“localhost 页面表现正常”写成“当前 checkout 已验证”。

这个区分对 frontend、CU、twcu 尤其重要：

▎ 本地源码已经修改，但正在运行的服务仍是旧构建——这是非常现实的假通过来源。

我会直接采用这部分。

3. 它明确了“编写测试”发生在哪个阶段

见 docs/veripaka-target-shape.md:218。

它规定：

生成／修改测试与检查器
→ 完成方法准备
→ 冻结验证计划
→ 执行

执行中需要修改判断器，就保留当前记录并产生新计划。

这比笼统说“Recipe 可以指导创建测试”更完整，也更贴近 Draft 的 building test methods。

需要注意：冻结的是方法及允许的变化规则，不是禁止 property testing、探索测试生成新输入。输入可以按既定规则变化，判断标准不能临时变。

4. 它把“能复用”也当作需要验证的能力

这份的 reusable 要求不仅是：

- 好样本通过；
- 坏样本失败；

还包括冷上下文复用记录。

见 docs/veripaka-target-shape.md:256。

这很切中 Veripaka：

▎ 一份只有作者自己知道如何执行的方法，即使检出力不错，也没有充分证明它是一份可供 Agent 复用的 Recipe。

上一份将冷会话复用放在产品验收中；这份进一步放进方法成熟度，有价值。

但建议记录具体适用条件，例如宿主、工具与模型配置，而不是给一个永久通用的 reusable 标签。这份已经有这个方向。

5. 第一切片更克制，而且没有牺牲底线

见 docs/veripaka-target-shape.md:631。

它推迟自动发现、导出和更多执行器，但没有推迟：

- 非空必需检查集合；
- 目标身份；
- 证据来源；
- 缺失与中断拒绝规则。

这是正确的缩小方式：

▎ 缩小支持范围，而不是降低已支持范围的真实性。

上一份第一阶段同时承担 init、导入、创建、搜索、执行、Profile、宿主消费，还是偏宽。

四、我会修改这份的几个地方

1. provenance 目前混合了不同维度

这份列出的：

command-captured
tool-self-reported
agent
human
imported

不是同一分类轴。

- agent/human：谁生成或解释。
- command-captured：怎样采集。
- imported：怎样进入当前系统。
- tool-self-reported：信息由谁声明，以及验证程度。

例如，一份 CI runner 生成、带可核验身份的报告，进入本地时也是 imported；这不意味着它永远不能支持 executable claim。

这份禁止自由导入材料直接满足 executable claim，作为首版限制是合理的；但不应固化为永恒的领域语义。

建议概念上分开：

producer       谁产生
ingestion      怎样接入
verification   验证了哪些关联
judge          谁／什么解释结果

首版可以只支持少量组合，不必增加复杂信任框架。

关键规则应该是：

▎ 自由导入不能自称可信；是否能支持 claim，取决于计划要求和已验证的来源链，而不是仅取决于“是否经过导入”。

2. 保留 apply/run/collect/finalize 的内部语义，但不要强迫每次走四个手工命令

这份的协议切分是好的，但它也是 Agent 需要遵循的一条多步流程。

如果弱模型必须记住：

1. apply；
2. run；
3. collect；
4. finalize；

遗漏 finalize 本身就会成为新的故障模式。

建议：

- command 模式：run 自动完成受管采集和 finalize。
- agent-guided 模式：保留 collect/finalize，但返回明确下一步和缺失项，由 Skill 引导。
- 低层命令保持可用，服务外部工具和恢复流程，不作为所有用户的默认操作面。

即：

▎ 协议可以分阶段，日常体验不必同样碎片化。

这里并不要求 pi extension；普通 CLI 和 Skill 就可以先做到。

3. “验证”和“调查”的区别应进入结构，不只写在正文中

这份已经正确解释纯探索不能输出无缺陷保证，但样例和最小 schema 尚未明确承担这个区别的字段。

technique: exploratory 不宜单独决定结果语义：它是测试技术，不一定等于整个任务的性质。

建议采用上一份的明确区分，例如：

kind: verification
# 或 investigation

然后分别定义完成条件：

- verification：必需行为主张的结果与证据。
- investigation：探索目标、时间盒、记录与停止条件。
- 调查完成可以成功结束，但不产生“被测产品通过”的业务结论。

这会让 finalize 的分支更清楚，而不是依靠模型理解正文中的例外。

4. 采用 docs/verification/，但不要让 README 同时承担人工入口和全量生成索引

我现在更倾向这份的默认目录：

docs/verification/   方法资产
.veripaka/           运行数据

因为 Veripaka 的长期资产本来就是应该被人阅读、审查和修改的方法文档。可配置单一 corpus root 也解决了团队惯例问题。

不过，我会保留上一份的 README 策略：

- README：稳定入口、约定、使用方法。
- 索引：CLI 实时查询，或单独生成 INDEX.md。
- 索引不是权威来源，缺失或过期不改变方法定义。

原因不是生成索引难，而是用户能直接编辑 Recipe，CLI 未必知道什么时候需要同步已提交 README。第一版没有必要制造这一同步负担。

5. “第一版串行”仍需覆盖两个会话同时启动

这份已经指出主机级资源协调，方向正确。但应该把最低限度的约束明确前置，而不是留给将来的并发功能。

具体来说：

- 第一版 command 执行至少避免 run 产物互相覆盖。
- 进入自动 CU 场景前，同一桌面必须由工具已有互斥或最小主机级协调保护。
- 若没有协调能力，不能因为“单个 plan 内串行”就假定两个 plan 不会冲突。

这不是提前实现并行调度，而是防止已有串行执行互相干扰。

五、两份共同还没有完全收敛的关键点

“选中的检查全部通过”如何对应“用户这次的问题已回答”？

这份已经在 docs/veripaka-target-shape.md:435 区分：

1. 协议有效性；
2. 断言成立性；
3. 目标充分性。

这是正确认识，但 Plan 还可以再增加一个很轻的连接。

例如用户要求：

▎ 检查设置保存是否正确。

Agent 只选择 build 和 typecheck。它们满足：

- required 非空；
- 对象身份正确；
- 真实执行；
- 全部通过。

所有执行契约都成立，方法选择却没有回答用户的问题。

建议 Plan 保存一个简单映射，不需要新引擎：

┌────────────────────┬───────────────────┬──────────────────────┐
│ 本次需要回答的问题 │  对应方法／claim  │      未覆盖部分      │
├────────────────────┼───────────────────┼──────────────────────┤
│ 设置操作是否成功   │ 保存交互检查      │ —                    │
├────────────────────┼───────────────────┼──────────────────────┤
│ 刷新后是否保留     │ persistence claim │ —                    │
├────────────────────┼───────────────────┼──────────────────────┤
│ 是否跨设备同步     │ 未选择方法        │ 不在本次范围／待验证 │
└────────────────────┴───────────────────┴──────────────────────┘

这个映射仍由 Agent/人判断，不会自动证明充分性。但它让“为什么选这些方法”和“哪些问题没回答”成为执行前可审查、执行后必须保留的内容。

否则系统容易在执行侧越来越严谨，选择侧仍依赖一句“我认为这些够了”。

这比继续增加 receipt 字段更接近产品下一步的重要问题。

六、最终建议：主案怎么收敛

我建议采用以下组合，而不是平行维护两套方案：

主案采用这份

- docs/verification/＋.veripaka/。
- Recipe package 与项目绑定。
- command / agent-guided 两种执行模式。
- apply 的准备／冻结语义。
- 证据采集与检查器映射规则。
- 明确被测对象类型。
- reusable 的冷上下文要求。
- 单 npm 包、Skills、包内 launcher。
- 更小的 M1。

其中我会撤回上一份中将 mixed 单列为顶层执行模式的必要性：guided 本身可以调用脚本，混合判断应逐 claim 表达，无须再加一种模式。

从上一份补入

- verification / investigation 的显式区别。
- baseline 候选到接受的明确操作，自动方法修订只生成草稿。
- 第一版多进程冲突和 Windows 进程树处理。
- README 与生成索引分离。
- 把评估拆为“只有方法文档”与“文档＋CLI”，分清贡献来自哪里。

两份一起补齐

- provenance 正交化。
- command 一键执行、采集、汇总。
- 用户问题到方法/claim 的覆盖映射。

如果现在只能选择一份继续推进，我选 docs/veripaka-target-shape.md。 它已经不只是“方向正确”，而是更接近能指导实现的协议草案。下一步应修订上述少数边界，并用两条真实 Recipe 验证，而不是再扩写一份更长的第三版宏观方案。
